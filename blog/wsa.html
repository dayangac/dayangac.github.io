Building a Neural Network Accelerator

November 12, 2026

This is a small neural network accelerator built around a systolic array, written in Chisel. A host sends it a trained network and some inputs over a serial cable, the hardware runs every layer, and the host reads the answers back. Right now it classifies handwritten digits end to end in simulation. If you're interested in how ML accelerators like the TPU work, or just want to see one small enough to read in an afternoon, this post is for you.

What Can It Do

It runs fully connected networks (MLPs) with int8 weights and activations and int32 sums. The demo network is a small 64-32-10 classifier for 8x8 handwritten digits. It gets 96.7% on the held-out set, the same as the float version it was quantized from. In simulation, 32 test images go through the whole thing: bytes over the UART, both layers on a 4x4 array, results back over the UART. Every output matches a Python model of the hardware bit for bit, and all 32 digits come out right.

The array does 16 multiply-adds per cycle, and with a batch of 32 images it keeps about 96% of them busy. The whole batch takes about 5000 cycles, so around 50 microseconds at 100 MHz. That sounds fast until you look at the serial link, which I'll get to at the end. It has only run in simulation so far, not on an FPGA. Synthesis says it should fit on an ECP5 (about 5200 LUTs and 17 multipliers), which is the next step.

How It Works

The main parts are the:

  • Processing element
  • Systolic array
  • Engine
  • Host link

Processing Element

A systolic array is a grid of tiny identical cells that pass data to their neighbours every clock cycle. Each cell, a PE, does one multiply-add. The question is what stays put in each PE and what moves. In my design the weight stays put: each PE holds one weight, activations flow in from the left, and partial sums flow down from above. This is called weight-stationary, and it's the same idea as Google's TPU.

The trick that makes it fast is that each PE has two weight registers. While the PE computes with the active weight, the next weight loads into a shadow register behind it. A swap flag travels along with the first activation of the next tile, so each PE switches weights exactly when the new data reaches it, and the array never has to stop. This is pretty much the whole PE:

// double buffered, shadow loads while active computes
val shadow = RegInit(0.S(dataWidth.W))
val active = RegInit(0.S(dataWidth.W))
when(io.shift) { shadow := io.shiftIn }
when(io.swapIn) { active := shadow }

val weight = Mux(io.swapIn, shadow, active)

io.shiftOut := shadow
io.actOut   := RegNext(io.actIn, 0.S)
io.swapOut  := RegNext(io.swapIn, false.B)
io.psumOut  := RegNext(io.psumIn + weight * io.actIn, 0.S)

Systolic Array

Put n by n of these together and you get y = x W for a whole input vector every cycle. The one annoying part is timing: row r's activation has to arrive exactly when the partial sum from row r - 1 does, so each row is delayed by one more cycle than the row above it. The outputs get the opposite delay so the whole result vector comes out on the same cycle, 2n - 1 cycles after it went in.

In Chisel the whole grid is one loop. Each PE gets its weight from the PE above, its input from the PE on the left, and its partial sum from above. The ShiftRegister calls are the delays that line everything up:

val pes = Seq.fill(n, n)(Module(new PE(dataWidth, accWidth)))

for (r <- 0 until n; c <- 0 until n) {
  val pe = pes(r)(c)
  pe.io.shift   := io.shift
  pe.io.shiftIn := (if (r == 0) io.weightIn(c) else pes(r - 1)(c).io.shiftOut)
  pe.io.actIn   := (if (c == 0) ShiftRegister(io.actIn(r), r) else pes(r)(c - 1).io.actOut)
  pe.io.swapIn  := (if (c == 0) ShiftRegister(io.swap, r, false.B, true.B) else pes(r)(c - 1).io.swapOut)
  pe.io.psumIn  := (if (r == 0) 0.S else pes(r - 1)(c).io.psumOut)
}

for (c <- 0 until n) {
  io.out(c) := ShiftRegister(pes(n - 1)(c).io.psumOut, n - 1 - c)
}
io.outValid := ShiftRegister(io.inValid, latency, false.B, true.B)

Engine

A real layer is way bigger than 4x4, so the engine cuts it into 4x4 tiles. For each tile it loads the weights into the shadow registers, streams every input in the batch through the array, and adds the results into an accumulator memory. On the last tile it also adds the bias, shifts the result back down to int8 range, and applies ReLU. Hidden layer results go straight back into the activation memory in exactly the layout the next layer reads, so a layer sequencer can run up to 16 layers back to back without the host doing anything.

when(streaming) {
  issueValid := true.B
  io.aAddr   := actTileBase + row
  when(row === 0.U) {
    issueSwap  := true.B
    shadowFull := false.B
    sinceSwap  := 0.U
  }

The first row of every tile carries the swap. Then the loader is allowed to start filling the shadow registers again, but only once the swap has made it to the last PE, 2n - 2 cycles later. There's a test that starts the load one cycle earlier than that and checks that the results come out wrong, which is a nice way to know the limit is real.

This is the post processing on the way out. Adding half before the shift rounds to the nearest value instead of always rounding down, and the sum is two bits wider than the accumulator so it can't overflow before the shift:

val maxOut = ((1 << (dataWidth - 1)) - 1).S
val minOut = (-(1 << (dataWidth - 1))).S
// rounding shift, sum is 2 bits wider so it can't wrap
val half   = ((1.U << io.shift) >> 1).asUInt.zext

for (i <- 0 until n) {
  val sum     = io.in(i) +& io.bias(i) +& half
  val shifted = sum >> io.shift
  val v       = Mux(io.relu && shifted < 0.S, 0.S, shifted)
  io.out(i)        := v(accWidth - 1, 0).asSInt
  io.outClamped(i) := Mux(v > maxOut, maxOut, Mux(v < minOut, minOut, v))(dataWidth - 1, 0).asSInt
}

Host Link

The board talks to the computer over a UART. A small command parser reads bytes and turns them into memory writes: weights, biases, inputs, layer configs, then "run" and "read results". A Python script on the other end trains the network with numpy, quantizes it to int8, and builds the byte stream.

The parser is a small state machine. The first byte says which command it is, and that decides how many header bytes to read next:

is(State.Idle) {
  when(got) {
    cmd    := byte
    hdrIdx := 0.U
    switch(byte) {
      is(Cmd.WriteWeights.U, Cmd.WriteBias.U, Cmd.WriteActs.U, Cmd.ReadOut.U) {
        hdrLen := 4.U
        state  := State.Header
      }
      is(Cmd.WriteLayer.U) {
        hdrLen := 15.U
        state  := State.Header

How I Made It

I built this over the summer of 2026, on my own. I had only done a little hardware design before, so the project was also how I learned Chisel. I come from software, and that shaped the order I worked in: write the smallest piece, check it against a plain model of what it should do, and only then build on it.

The design is written in Chisel, which lets me write Scala that generates the Verilog. Every module has its own test, run in Verilator through ChiselSim. I started with one PE and checked a whole array of them against a reference matrix multiply for sizes 1 to 8. Double buffering the weights came next, then the post processing, the tiling engine, the layer sequencer, the UART and the command parser, in that order. Verilator builds were most of the test time, so the array tests share one simulation per size.

The part that taught me the most was the host side. In September I wrote a bit exact Python model of the hardware and the byte protocol. In October I trained the digits network with numpy, quantized it to int8, and ran it through the UART in simulation, where all 32 test images came out right. I never ran it on an FPGA, so the only hardware numbers I have are the resource counts from yosys.

What's Next?

The funny part is that the array isn't the bottleneck at all. Sending the network and the 32 images over a 115200 baud UART takes about half a second, and the actual math takes 50 microseconds. So the first easy wins are on the I/O side: keep the weights on the chip instead of resending them with every batch, send back only each image's predicted digit instead of all the raw outputs, and use a faster link. After that, I want to make small batches faster (right now loading weights dominates when the batch is under about 12 images), and actually get it running on an FPGA.

That last one needs a real board, so the next step is getting an FPGA of my own. Everything so far has been simulation and synthesis reports, and I want to see this thing run on hardware, where timing, clocks and the memory ports stop being theoretical.

The bigger goal is to keep working on hardware for machine learning: TPU-style accelerators, and further out, chiplets and the packaging and interconnect that tie several dies into one system. This project is a small first step in that direction, and I want to build on it.
